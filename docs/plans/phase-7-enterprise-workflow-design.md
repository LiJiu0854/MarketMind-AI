# 单元 7：研究报告审核与交付设计

**状态：** 待用户审阅正式设计文档；本文件不是实施许可。

## 1. 目标和边界

单元 6 已把受控研究结果、证据和费用保存在 MySQL，但结果尚不能进入有负责人、决定和交付记录的业务流程。单元 7 的目标是让管理员审核一份有证据支持的研究报告，留下不可修改的审核决定，再让团队下载标明审核结果和来源的 Excel 报告。这使研究结论从“模型生成的结果”变为“有人负责、可追溯、可交付的运营资料”。

本单元沿用项目的教学与工程约束：四个 Task，先写测试并观察 RED，再做最小实现和 GREEN；每个 Task 生成一份只保留本地、不提交 Git 的中文学习文档，解释真实编写顺序、类与函数的职责、调用来源、关键代码原理、故障和验收。优先便于理解，同时保持实际业务价值。用户既有的学习文件和练习测试不修改、不暂存。

本设计不调用新模型，不自动联网采集，不接飞书、钉钉、企业微信或 ERP，不做通用 Webhook/MCP/工作流引擎、Playwright/RPA、Vue 页面、定时研究或自动修改商品。没有真实企业系统目标时，不为假设中的接口建立抽象。外部交付由人员下载已批准文件完成；未来确定目标系统后，再为该系统单独设计受限适配器。

## 2. 方案选择

| 方案 | 优点 | 代价与结论 |
|---|---|---|
| 直接接企业系统 | 可以自动推送 | 没有目标系统、认证方式及数据契约，无法可靠验收；不采用 |
| 通用工作流与连接器平台 | 表面上扩展性高 | 当前只有一条业务流程，增加状态与安全面；不采用 |
| **研究报告 → 人工审核 → Excel 交付** | 可审计、可测试、复用现有 MySQL/FastAPI/openpyxl | 首版仍需人工下载与传递；本单元采用 |

## 3. 业务状态与不可变性

只有 `research_runs.status = success` 且结构化报告 `outcome = supported` 的研究可审核。`pending/running` 尚无报告，`failure` 没有可信报告，`insufficient_evidence` 不能冒充已证实结论；这些状态不能批准或导出“已批准”交付件。审核不修改研究步骤、证据或原始报告。

一份可审核报告至多有一条终局审核记录：`approved` 或 `rejected`。没有审核记录表示 `pending_review`；尚未完成的研究显示 `not_ready`，失败或证据不足显示 `not_reviewable`。一旦批准或驳回，原审核记录不可覆盖、撤销或删除。驳回后需补充资料并发起新的研究，而不是在旧研究上改写报告。原研究与驳回意见继续保留。

管理员填写 `decision` 和最多 500 字符的 `comment`；驳回意见去首尾空格后必须非空，通过意见可省略。相同管理员用完全相同的规范化决定和意见重试，返回已存在的审核记录；不同管理员或不同内容再次提交返回稳定 `409`，不产生第二条记录。此幂等规则只用于安全处理客户端超时后的重试，不允许改变已作决定。

## 4. 数据模型与事务

Alembic `0006` 新增 `research_report_reviews`，不改 `research_runs.report`。字段为 `id`、唯一且非空的 `run_id` 外键、`reviewed_by_id` 外键、限定为 `approved/rejected` 的 `decision`、可空 `comment`、`reviewed_at`。研究 ID 的数据库唯一约束是并发下的最终保护；审核时间由服务端生成。审核人必须是当前认证的 Admin，不能由请求体指定。

审核事务先以 `SELECT ... FOR UPDATE` 锁定目标 `ResearchRun`，并同时核对 URL 中 `product_id` 与记录归属、研究终态及报告格式，再读取或插入审核记录。这样两个管理员不会同时通过“未审核”的检查。若唯一约束仍因竞争命中，回滚并重新读取已存在记录，按上述幂等规则返回或报 `409`；不得把数据库异常原文返回给客户端。事务只包围本地数据库操作，不调用模型或外部网络。

读取研究详情时联取/单独读取该研究的审核记录，向客户端返回派生的 `review_status` 与可空 `review` 信息。列表可以只增加 `review_status`，不把审核全文重复铺到每一行；必须避免分页后的 N+1 查询。所有数据仍按研究原有的商品归属边界读取，其他商品的 `run_id` 返回 `404`。

## 5. API、权限和错误契约

所有接口继续使用已有 JWT、`require_roles`、`get_db_session`、统一 `AppError` 与异常处理；知识库和研究仍是团队共享，不新增租户概念。

| 接口 | 权限 | 结果 |
|---|---|---|
| `POST /api/v1/products/{product_id}/research-runs/{run_id}/review` | Admin | 请求 `decision/comment`；新决定返回审核详情；完全相同重试返回同一详情 |
| `GET /api/v1/products/{product_id}/research-runs/{run_id}` | Admin、Operator、Analyst | 在现有研究详情上增加审核状态和记录 |
| `GET /api/v1/products/{product_id}/research-runs/{run_id}/export` | Admin、Operator、Analyst | 仅已批准报告返回 `.xlsx` 下载 |

未登录 `401`，无审核权限 `403`，商品或该商品下研究不存在 `404`，不可审核/不可导出/相互冲突的审核 `409`，请求字段无效 `422`。稳定错误码与中文安全说明供客户端判断，不能泄露数据库异常、Token、密钥或原始模型响应。审核成功后不会自动发送邮件或向外部系统推送。

## 6. Excel 交付件

复用项目已有的 `openpyxl`、`BytesIO`、`StreamingResponse` 生成内存中的 `.xlsx`，不落地临时文件，也不新增报表依赖。文件名只使用数字研究 ID，例如 `research-123.xlsx`，避免商品标题或资料文件名进入响应头。响应只允许在服务端重新查询并确认 `approved` 后生成，不能相信客户端提供的审核状态。

固定工作表为“概览”“发现与建议”“证据”。概览包含商品 SKU/标题快照、研究目标、报告摘要、报告结论、研究 ID、审核决定/管理员/时间；发现与建议列出原报告的声明、行动、理由和 `source_id`；证据表列出每个来源 ID、来源类型、已登记的文件名/页码/片段等。报告正文与证据坐标均取自单元 6 已持久化且经过校验的数据，不重新询问模型或实时检索 Chroma。导出不暗示资料一定真实，表中应注明“结论基于已上传且经程序核验的资料，仍需业务复核”。

商品字段、摘要、发现、建议、文件名和证据摘录都可能是外部输入。写入单元格前统一将以 `=`、`+`、`-`、`@` 等公式前缀（包括前置空白后出现）开头的文本按纯字符串安全化，测试重新打开工作簿确认其不是公式。保持数值 ID 和时间的正常类型；不允许用户输入决定工作表名、公式、超链接或文件路径。Excel 生成有界于单元 6 的报告/证据上限，下载不保存审计副本；审核记录是交付决策的审计来源，首版不另建下载日志表。

## 7. Task 拆分与验收

1. **Task 1：审核模型、迁移与 Schema。** 先测唯一研究 ID、外键、决定枚举、驳回必填意见、审核状态派生，再实现 `0006` 与类型边界。
2. **Task 2：审核事务、权限与 API。** 先测研究资格、商品归属、Admin 权限、相同请求重试与双管理员并发，再实现短事务和路由；详情/列表展示审核状态。
3. **Task 3：安全 Excel 报告。** 先测未批准拒绝、三个工作表、引用追溯、公式注入和内存下载，再实现导出服务与路由。
4. **Task 4：跨层验收与教学收尾。** 补齐 README、错误与权限矩阵、迁移验证、完整自动化和四份本地中文学习文档；检查没有误提交用户文件。

每个 Task 的测试必须先出现与目标行为一致的失败，再实现最小代码并复验。最终执行工程全量 pytest、Ruff、mypy、迁移与 Git 差异检查；原样测试结果与用户未跟踪练习测试的已知失败分开报告。所有模型/向量调用在自动化测试中模拟，不进行付费真实调用。单元 7 基于当前 `codex/phase-6-agent-research` 的完成提交开展，不能误认为可以单独从尚未整合的 `main` 运行；未经用户明确要求不推送或合并。

## 8. 完成标准与剩余限制

Admin 能对有证据报告作一次不可篡改的通过/驳回；并发和重试结果一致；团队能查看审核状态，且仅能下载已批准、带来源且不会执行文本公式的 Excel。研究原件和报告内容不因审核改变，所有失败有安全错误。此时单元 7 形成完整的**内部**审核交付闭环，但不是自动同步到外部企业系统；外部集成、前端与 CI/部署分别待真实目标和后续单元再设计。
